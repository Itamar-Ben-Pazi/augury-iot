# מערכת IoT – בדיקות חומרה ואוטומציה

## 1. תיאור הפרויקט

הפרויקט מדמה מערכת IoT קטנה באמצעות Python ו־Robot Framework.

המערכת כוללת צמתים (Nodes), חיישנים (Endpoints), עדכוני תוכנה לצמתים באמצעות OTA ועדכוני קושחה לחיישנים באמצעות DFU.

כל הפעולות מתבצעות בסימולציה מקומית, ללא שימוש בחומרה אמיתית, שרתים או שירותי ענן.

## 2. מבנה הפרויקט

### תיקיית iot

- `node.py` – מימוש מחלקת Node והלוגיקה של עדכוני OTA.
- `endpoint.py` – מימוש מחלקת Endpoint וחוקי עדכון DFU.
- `api.py` – ממשק המאפשר גישה למערכת וביצוע פעולות.
- `__init__.py` – קובץ המסמן את התיקייה כחבילת Python.

### תיקיית tests

- `ota_happy.robot` – בדיקת עדכון OTA תקין.
- `endpoint_dfu.robot` – בדיקת עדכון חיישן בהתאם ל־Backlog ולמצב הסוללה.
- `bad_firmware.robot` – בדיקת דחיית קובץ עדכון שאינו מתאים לסוג החומרה.

## 3. דרישות והתקנה

נדרש Python 3.10 ומעלה ו־Robot Framework.

כדי להתקין את הספריות הנדרשות, יש לפתוח טרמינל בתיקייה הראשית של הפרויקט ולהריץ:

`python -m pip install -r requirements.txt`

## 4. הרצת הבדיקות

כדי להריץ את כל הבדיקות, יש לבצע:

`python -m robot --pythonpath . tests/`

בסיום ההרצה Robot Framework יוצר את הקבצים:

- `report.html` – דוח מסכם של תוצאות הבדיקות.
- `log.html` – פירוט הפעולות שבוצעו בכל בדיקה.
- `output.xml` – תוצאות ההרצה בפורמט XML.

## 5. תכנון המערכת

המערכת מבוססת על שלוש מחלקות מרכזיות.

### מחלקת Node

מייצגת צומת שמנהל חיישנים ומקבל עדכוני OTA.

סוגי הצמתים הנתמכים הם AHN2, CASSIA ו־MOXA.

כל Node שומר את גרסת התוכנה הנוכחית שלו, את החיישנים המחוברים אליו, את ערוץ ה־OTA ואת מצב תהליך העדכון.

### מחלקת Endpoint

מייצגת חיישן המחובר ל־Node.

סוגי החיישנים הנתמכים הם EP1, EP2 ו־Canary_A.

כל Endpoint שומר את המספר הסידורי שלו, גרסת הקושחה, מצב הסוללה וכמות הדגימות שממתינות להעברה (Backlog).

החיישן אחראי לבדוק האם מותר לבצע עדכון DFU בהתאם לתנאים שנקבעו.

### מחלקת API

מספקת ממשק אחיד לפעולות במערכת.

ה־API מאפשר ליצור Nodes, להוסיף חיישנים, לקבל מידע ולבקש עדכוני OTA ו־DFU.

ה־API מאתר את האובייקט המתאים ומעביר אליו את בקשת הפעולה. הלוגיקה עצמה נמצאת במחלקות Node ו־Endpoint.

## 6. הנחות והחלטות תכנון

### עדכוני OTA

- עדכון OTA אינו מתבצע מיד לאחר פרסום קובץ העדכון.
- בחרנו לדמות עדכון שמתבצע לאחר שתי פעולות Polling.
- בדיקות Robot מבצעות עד שלושה ניסיונות, עם מרווח של 100 מילישניות בין ניסיונות שנכשלו.
- קובץ עדכון מתקבל רק אם סוג החומרה שלו תואם לסוג החומרה של ה־Node.
- ההשוואה בין סוגי החומרה אינה רגישה לאותיות גדולות וקטנות.
- קובץ לא מתאים נדחה, וה־API מחזיר 400.
- במקרה של שגיאה, ניתן לקבל הסבר דרך השדה `last_error`.
- ניקוי ערוץ OTA מתבצע באמצעות פעולה מפורשת.

### עדכוני DFU

- עדכון DFU נחסם אם לחיישן יש Backlog גדול מאפס.
- כדי לדמות העלאת דגימות, הוגדרה פעולה שמרוקנת את ה־Backlog לאפס.
- כאשר ה־Backlog ריק, ניתן לבצע עדכון בתנאי שהסוללה עומדת בסף הנדרש.
- עבור EP1 ו־EP2 סף הסוללה הוא 2500.
- עבור Canary_A סף הסוללה הוא 3600.
- כאשר תנאי העדכון אינם מתקיימים, גרסת החיישן נשארת ללא שינוי.

### החלטות נוספות

- כל Node יכול להכיל חיישן אחד מכל סוג.
- המספר הסידורי של כל חיישן חייב להיות ייחודי.
- אובייקטי ה־Node נשמרים במילון במחלקת API.
- כל Node מנהל בעצמו את החיישנים המשויכים אליו.
- המערכת שומרת את המידע בזיכרון בלבד, ללא בסיס נתונים.
- לא נדרש חיבור לשרת או לחומרה אמיתית.

## 7. תרחישי הבדיקה

### TC1 – עדכון OTA תקין

יוצרים Node בגרסה 33, מפרסמים קובץ עדכון מתאים לגרסה 34 ומבצעים Polling עד שהגרסה משתנה.

הבדיקה מוודאת שהעדכון התקבל, שהגרסה אינה משתנה מיד לאחר הפרסום ושהיא מתעדכנת לאחר פעולות ה־Polling.

### TC2 – עדכון DFU עם Backlog

יוצרים חיישן בעל Backlog חיובי ומוודאים שעדכון DFU נחסם.

לאחר ריקון ה־Backlog מוודאים שהעדכון מצליח.

בנוסף, מורידים את רמת הסוללה מתחת לסף הנדרש ומוודאים שעדכון נוסף נחסם ושהגרסה אינה משתנה.

### TC3 – קובץ OTA לא מתאים

יוצרים Node מסוג Cassia ומנסים לעדכן אותו באמצעות הקובץ `moxa_34.swu`.

הבדיקה מוודאת שהקובץ נדחה, שגרסת ה־Node אינה משתנה ושמתקבלת הודעת שגיאה.
